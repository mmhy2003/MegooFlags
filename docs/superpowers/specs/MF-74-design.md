# MF-74 — Foundation: repo scaffold, versioning, CI and release pipeline

## Goal
Turn the empty `mmhy2003/MegooFlags` repo into a releasable monorepo: an empty but working FastAPI `api/` and Next.js `web/`, one shared version, CI that enforces every rule in PRD §8.4, and a tag-driven release that publishes multi-arch images to GHCR. Done when the empty app builds, CI is green, and the test tag `v0.1.0-rc.1` publishes images.

## Decisions
- **PRD Q6, SDK location: in this repo** under `sdks/<lang>/`, each SDK with its own tag prefix (`sdk-node/v1.2.0`, and Go's required `sdks/go/v1.2.0`). Server tags stay `v*`. This task only reserves the layout: `sdks/README.md` documents the tag scheme and `spec/README.md` reserves the shared evaluation spec and conformance suite. No SDK code or SDK workflows yet. *Rejected:* separate repos per SDK, and a hybrid. The PRD Q6 answer should also be written into the PRD's open questions.
- **Test releases: also accept `vX.Y.Z-rc.N` tags.** An rc publishes only its exact image tag (`0.1.0-rc.1`), never `X.Y`, `X` or `latest`, and is always a GitHub pre-release. *Rejected:* burning a real `v0.1.0`, or a `workflow_dispatch` dry run.
- **Package managers: uv for Python (`uv.lock`), pnpm for JS (`pnpm-lock.yaml`, pinned with `packageManager`).** Installs are frozen in CI and in the Dockerfiles. *Rejected:* npm, and pip.
- **Native arm64 runners** (`ubuntu-24.04-arm`) build arm64 images, and a final job merges the per-arch digests into one manifest. This avoids slow QEMU builds of Next.js. If arm runners are not available, QEMU on a single runner is the fallback.
- **One baseline Alembic revision (`0001_baseline`, no-op)** so that the single-head and upgrade/downgrade checks run on something real from day one.

## Architecture (repo layout)

```
AGENTS.md                    agent rules (below); CLAUDE.md = "@AGENTS.md" + Claude-only notes

  src/megooflags_api/        main.py (app factory), settings.py (pydantic-settings, MEGOOFLAGS_*),
                             db.py (async engine/session, asyncpg), routers/health.py,
                             export_openapi.py
  alembic/                   env.py (async), versions/0001_baseline.py
  tests/
web/                         package.json (version = VERSION), pnpm-lock.yaml, Dockerfile
  next.config.ts             output: "standalone"
  app/ (App Router placeholder page), components/ui (shadcn init), lib/api/
  lib/api/schema.d.ts        generated by openapi-typescript from api/openapi.json
  lib/api/client.ts          openapi-fetch typed client
api/openapi.json             committed spec produced by export_openapi.py
deploy/                      docker-compose.yml, Caddyfile (PRD §8.2), .env.example (recommends pinning MEGOOFLAGS_VERSION)
                             compose.ci.yml (override: locally built images for the smoke test)

sdks/README.md, spec/README.md   reserved (see Decisions)
.github/workflows/ci.yml, release.yml
```
- **api:** Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2 async + asyncpg, Uvicorn, Alembic. Dev tools: ruff, mypy (strict on `src/`), pytest, pytest-asyncio and httpx.
- **web:** Node 22 LTS, Next.js 16, React 19, TypeScript strict, Tailwind 4, shadcn/ui init, ESLint 9 flat config, Prettier. No theming or app shell yet (later tasks).
- **Images:** `api/Dockerfile` is multi-stage on `python:3.12-slim`, runs `uv sync --frozen --no-dev`, runs as a non-root user and starts Uvicorn on :8000. The `migrate` service uses the same image with `alembic upgrade head`. `web/Dockerfile` is multi-stage on `node:22-alpine` with pnpm, copies the standalone output, runs as non-root and serves on :3000. Both carry OCI labels with the version and git revision.
- **Compose and Caddy:** these follow PRD §8.2 (caddy, web, migrate → api, db: postgres:16). The Caddyfile also routes `/healthz` and `/readyz` to `api`.

## Data and interfaces
- `GET /healthz` → `200 {"status":"ok","version":"0.1.0"}`. This is a liveness check with no dependencies.
- `GET /readyz` → `200 {"status":"ready"}` after a `SELECT 1` succeeds, and `503 {"status":"not_ready"}` when the database is unreachable.
- Config: `MEGOOFLAGS_DATABASE_URL`, `MEGOOFLAGS_VERSION`, `MEGOOFLAGS_SITE_ADDRESS`, `MEGOOFLAGS_TRUSTED_PROXIES`, `MEGOOFLAGS_PUBLIC_URL`, `MEGOOFLAGS_HTTP_PORT`. All of them go in `.env.example`, and the DB URL is used now.
- Typed client: `pnpm gen:api` regenerates `schema.d.ts` from `api/openapi.json`. CI re-exports the spec and fails if either file differs (drift check).

## CI (`ci.yml`, on pull requests and pushes to `main`; also callable with `workflow_call`)
Jobs run in parallel where possible:
1. **version:** `scripts/check_version.py`.
2. **api-lint:** `ruff check`, `ruff format --check`, `mypy`.
3. **api-test:** pytest against a `postgres:16` service container.
4. **migrations:** single-head check (`alembic heads` returns exactly 1). Then `upgrade head`, followed by a walk down and back up every revision (`downgrade -1` repeated to base, then `upgrade head`), against Postgres.
5. **web:** `pnpm install --frozen-lockfile`, `eslint`, `prettier --check`, `tsc --noEmit`, `next build`, plus the OpenAPI/client drift check.
6. **images:** `docker buildx build` of both images without pushing (with GHA cache).
7. **smoke:** builds the images, runs `docker compose -f deploy/docker-compose.yml -f deploy/compose.ci.yml up -d --wait`, then curls `/healthz`, `/readyz` and `/` through Caddy, and dumps the logs on failure.

## Release (`release.yml`, on tags `v[0-9]+.[0-9]+.[0-9]+` and `v[0-9]+.[0-9]+.[0-9]+-rc.[0-9]+`)
1. `check_version.py --tag <tag>`: the X.Y.Z part of the tag must equal `VERSION`.
2. Calls `ci.yml` (the full suite).
3. Builds `megooflags-api` and `megooflags-web` for linux/amd64 and linux/arm64 on native runners, pushes them by digest, then creates the manifest lists on `ghcr.io/mmhy2003/`. The tags are computed by a small step:
   - **rc:** `X.Y.Z-rc.N` only.
   - **final:** `X.Y.Z`, `X.Y` and `latest`, plus `X` only when X ≥ 1.
4. Creates the GitHub Release with `gh release create`. Notes are taken from the `CHANGELOG.md` section for X.Y.Z (rc tags fall back to `[Unreleased]` if that section is missing). The release attaches `docker-compose.yml`, `Caddyfile` and `.env.example`. It is marked `--prerelease` when X = 0 or the tag is an rc.

Permissions: `contents: write` and `packages: write`, used only in this workflow.

## AGENTS.md content
- X.Y.Z and 0.Y.Z bump rules with examples.
- Bump `VERSION`, `api/pyproject.toml`, `web/package.json` and `CHANGELOG.md` together in one commit.
- Every schema change needs an Alembic migration with a working `downgrade`; breaking changes follow expand/contract over two releases.
- Run the CI checks locally before opening a PR (exact commands listed).
- Regenerate the API client after any API change.
- Agents never push `v*` (or `sdk-*`) tags and never publish releases; a maintainer does.
- The SDK tag scheme for `sdks/`.

## Edge cases
- A tag that does not match `VERSION` fails before anything is built or pushed.
- An rc tag never moves `latest` or `X.Y`.
- The `X` tag is never produced for 0.Y.Z.
- If the CHANGELOG section is missing for a final tag, the release fails rather than publishing empty notes.
- `/readyz` returns 503 rather than hanging when the DB is down (short connect timeout).

## Testing
- **pytest:** `/healthz`; `/readyz` with the DB up and with a bad DB URL; `check_version.py` (match, mismatch, valid and invalid tag formats, rc handling); the image tag computation (0.1.0, 0.1.0-rc.1, 1.4.2).
- **CI:** the migrations job and the compose smoke test (above).
- **Acceptance:** CI is green on the PR. After merge, a maintainer pushes `v0.1.0-rc.1`, and both images appear on GHCR for amd64 and arm64 with only the `0.1.0-rc.1` tag, together with a pre-release that has the three assets.

## Out of scope
- SDK code and SDK release workflows.
- Multi-node compose files (`control-plane` and `worker`).
- Theming and the app shell.
- Playwright accessibility checks (UI-19).
- Branch protection settings (configured by the maintainer in GitHub).
- Pushing the real `v0.1.0`.
