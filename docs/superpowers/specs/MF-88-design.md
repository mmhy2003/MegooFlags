# MF-88 design: Helm chart for MegooFlags

## Scope of this task

MF-88 lists six independent Phase 2 pieces. You chose the **Helm chart** as the piece this task designs and builds. The other five (experimentation, guarded rollouts, code references, observability integrations, control-plane HA) are not covered here and need their own tasks. I cannot create tasks in this stage, so please split them off; MF-88 could then be renamed "Helm chart".

Note: GA has not happened (`VERSION` is 0.1.0, `docs/ga-checklist.md` says "not ready"). The chart lands on `develop` before 1.0.0. It changes no API, database or web code.

## Goal

A user with a Kubernetes cluster can install MegooFlags with one `helm install` from `oci://ghcr.io/mmhy2003/charts/megooflags`, in any of the three roles the Compose bundles cover today: single node, control plane, or workers.

## Decisions

| Decision | Chosen | Why, and what was rejected |
|---|---|---|
| Roles | All three: `standalone`, `control-plane`, `worker` (your answer) | Same coverage as the Compose bundles. Rejected: no workers, or waiting for an API change that lets replicas share a token. |
| Entry point | Kubernetes-native routing, no Caddy (your answer) | Clusters already have an ingress controller or Gateway. Rejected: Caddy inside the chart, or both. |
| PostgreSQL and Valkey | Bundled by default, replaceable (your answer) | `helm install` works with no other setup, like Compose. Rejected: external only; Bitnami subcharts (their free images moved to a legacy repository in 2025). |
| Version and publishing | Chart version = server `VERSION`, pushed to GHCR as an OCI chart by `release.yml` (your answer) | One bump, one tag. Rejected: own chart version and tag; a classic Helm repository on GitHub Pages. |
| One role per release | A release is either a control plane (or single node) or a set of workers | Node tokens are created on the Nodes page after the control plane runs, so it is two steps anyway. It also matches the separate Compose files. |
| Workers | A StatefulSet where each replica has its own node token and its own volume | The control plane tracks one worker per token (heartbeat, drain, Nodes page). A small shell wrapper in the pod picks `token-<ordinal>` from a Secret, so the API needs no change. |
| Migrations | A plain Job per Helm revision runs `alembic upgrade head`; API pods have an init container that waits until the database is at the image's Alembic head | Same order as Compose (`api` starts after `migrate`). Rejected: a `pre-install` hook (the bundled database does not exist yet); `post-install` hook (deadlocks with `helm install --wait`); running Alembic in every API pod (replicas would race, Alembic takes no lock). |
| `MEGOOFLAGS_SECRET_KEY` | Required, never generated by the chart | A generated key changes on re-render in GitOps tools, which would make stored SSO and TOTP secrets unreadable and change the snapshot signing key. Compose also requires it. |
| Bundled PostgreSQL password | Defaults to `megooflags`, as in Compose, with a documented way to change it | Keeps the one-command install. A generated password has the same re-render problem. The Service is cluster-internal only. |
| Image tag | Defaults to the chart's `appVersion` | A chart of release X installs images of release X; no `latest` on Kubernetes. |
| Docs source | The chart's `README.md`, synced into the docs site | The repository already does this for SDK and Terraform READMEs (`site/sync.manifest.json`). |

## Architecture

The chart lives in `deploy/helm/megooflags/` (`Chart.yaml`, `values.yaml`, `values.schema.json`, `templates/`, `README.md`).

```text
Release A: role = standalone or control-plane        Release B: role = worker

 Ingress and/or HTTPRoute                             Ingress and/or HTTPRoute
   /api /sdk /ofrep /healthz /readyz -> api             /sdk /ofrep /healthz /readyz -> worker
   everything else                   -> web             everything else: not routed
        |                    |                                 |
   Service api:8000     Service web:3000                 Service worker:8000
        |                    |                                 |
   Deployment api       Deployment web                   StatefulSet worker (N replicas)
   (init: wait for      (MEGOOFLAGS_API_URL               each replica: token-<n> from the
    migrations)          = api Service)                   Secret, own volume at
        |                                                 /var/lib/megooflags
   Job migrate-<revision>                                      |
        |                                                 control plane URL
   StatefulSet postgresql (optional) + PVC                (public https URL, or the api
   Deployment valkey (optional)                            Service of release A)
```

- **Routing** copies the path lists of `deploy/Caddyfile` and `deploy/Caddyfile.worker`. `/metrics` is never routed, so it stays private. The chart can render an `Ingress` (`networking.k8s.io/v1`), a Gateway API `HTTPRoute`, both, or neither.
- **HTTPRoute extras**: rules that go to the API add `X-Content-Type-Options`, `Referrer-Policy` and `X-Frame-Options` with a `ResponseHeaderModifier` filter, and set `timeouts.request: "0s"` so SDK streams and the worker stream are not cut. Both are Extended features of the Gateway API, so each has a value to turn it off.
- **Ingress**: headers, buffering and idle timeouts are controller-specific. The chart passes `ingress.annotations` through, and the README lists what Traefik, HAProxy, ingress-nginx and the cloud load balancers need (no buffering, idle timeout above 60 s, the three API headers), like the existing reverse proxy guide.
- **Probes**: API and worker use `/healthz` (liveness) and `/readyz` (readiness). A worker is not ready until it has a snapshot, so `helm install --wait` on a worker release waits for the first sync.
- **Configuration**: non-secret settings go into a ConfigMap, secrets into a Secret. A checksum annotation restarts pods when either changes. Workers restart one at a time (StatefulSet rolling update).
- **Pods run as non-root** (uid 10001 for api and web, as in the images) with no privilege escalation.

Files outside the chart that change:

- `scripts/check_version.py`: also checks `version` and `appVersion` in `Chart.yaml`.
- `scripts/helm_test.sh` (new): the end-to-end test on kind.
- `scripts/tests/test_helm_chart.py` (new), `test_check_version.py`, `test_workflows.py`, `test_compose_files.py`.
- `.github/workflows/ci.yml`: a `helm` job. `.github/workflows/release.yml`: a `chart` job, and the `release` job attaches the `.tgz`.
- `site/sync.manifest.json` and `site/astro.config.mjs`: a "Kubernetes (Helm)" page under Deploy. Short pointers from `multi-node.md`, `upgrades.md`, `observability.md` and `security.md` (the API header note).
- `AGENTS.md` (layout, version bump list, local checks, releases), `CHANGELOG.md` (`[Unreleased]` / Added), `ROADMAP.md` (the Helm chart leaves Phase 2), `README.md`.

## Data and interfaces

No API, schema or environment variable changes. The new interface is the chart's values:

| Value | Default | Meaning |
|---|---|---|
| `role` | `standalone` | `standalone`, `control-plane` or `worker`. |
| `image.registry`, `image.tag`, `image.pullPolicy`, `imagePullSecrets` | `ghcr.io/mmhy2003`, the chart's `appVersion` | Where the api and web images come from. |
| `secretKey` | none | Required unless `role` is `worker` or `existingSecret` is set. At least 32 characters. |
| `existingSecret` | none | A Secret that replaces the chart's own, with the same keys: `MEGOOFLAGS_SECRET_KEY`, `MEGOOFLAGS_DATABASE_URL`, `MEGOOFLAGS_VALKEY_URL`, `POSTGRES_PASSWORD`; for workers `token-0`, `token-1`, … |
| `config` | the defaults of the Compose files | A map of `MEGOOFLAGS_*`, `OTEL_*` and `FORWARDED_ALLOW_IPS` variables. `MEGOOFLAGS_API_WORKERS` defaults to `2`, because the automatic count looks at the node's CPUs, not the pod's limit. |
| `api.*`, `web.*` | 1 replica each | `replicas`, `resources`, `extraEnv`, `podAnnotations`, `nodeSelector`, `tolerations`, `affinity`. |
| `postgresql.*` | enabled, `postgres:16`, 8Gi | `enabled`, `image`, `password`, `persistence.size`, `persistence.storageClass`, `resources`. |
| `externalDatabase.url` | none | Used when `postgresql.enabled` is false. Must use the `postgresql+asyncpg://` driver. |
| `valkey.*`, `externalValkey.url` | enabled, `valkey/valkey:8`, no persistence | As for PostgreSQL. |
| `worker.*` | none | `controlPlaneUrl` (required), `nodeTokens` (list; one replica per token), `replicas` (only with `existingSecret`), `controlPlaneInsecure`, `controlPlaneCa` (a ConfigMap or Secret with the PEM), `persistence.size` (1Gi), the usual pod settings. |
| `ingress.*` | off | `enabled`, `className`, `annotations`, `host`, `tls`. |
| `httpRoute.*` | off | `enabled`, `parentRefs`, `hostnames`, `apiResponseHeaders` (true), `timeouts.request` (`"0s"`). |
| `metrics.serviceMonitor.*` | off | A Prometheus Operator `ServiceMonitor` for the api or worker pods. |
| `migrate.annotations` | none | Extra annotations on the migration Job (see Argo CD below). |

Published artifacts per `vX.Y.Z` tag (and `-rc.N`): `oci://ghcr.io/mmhy2003/charts/megooflags:<version>` and `megooflags-<version>.tgz` on the GitHub release. `release.yml` packages with `--version` and `--app-version` set to the tag's image version, so a release candidate chart installs release candidate images. Agents never push; the workflow does. One maintainer step, once: make the GHCR package `charts/megooflags` public after the first push.

## Error handling and edge cases

- **Missing or bad values fail at render time with a message that names the value**: no `secretKey` (or shorter than 32 characters), `postgresql.enabled: false` without a database URL, the same for Valkey, a worker without `controlPlaneUrl` or without tokens, an unknown `role`.
- **A worker replica without its token key** (for example `replicas: 4` with three tokens) exits at once with a log line that names the missing key. The other replicas keep serving.
- **A migration fails**: the Job fails, new API pods stay in their init container, the old pods keep serving, and `helm upgrade --wait` fails. `kubectl logs job/<release>-migrate-<revision>` shows why. This is the Compose behaviour.
- **First install with the bundled PostgreSQL**: the migration Job first waits for the database to accept connections (up to five minutes), then migrates.
- **`helm rollback` across a migration** is not supported, as with Compose: the old image does not know the newer schema revision, so its pods never become ready and the running pods stay. The README says to restore the backup, as `upgrades.md` does.
- **Changing `postgresql.password` after the first install** does not change the password inside the existing volume (same as Compose). The README explains how to change it by hand.
- **`helm uninstall` keeps the volumes** of PostgreSQL and the workers. The README says how to delete them.
- **Upgrade order**: the control-plane release first, then the worker release, because of the version rule between workers and the control plane. Workers restart one at a time; a stopped worker closes its SDK streams within 5 s and the SDKs reconnect to the others.
- **Several API replicas**: only one runs the scheduler (PostgreSQL advisory lock) and they stay in sync through Valkey, as in `docker compose --scale api=N`.
- **Argo CD** renders charts without Helm revisions, so the Job name would not change between versions there. `migrate.annotations` lets Argo users mark the Job as a sync hook. This is documented but not tested in CI. Flux uses Helm itself and needs nothing special.
- **API responses behind a plain Ingress** do not carry the three security headers unless the controller adds them. Web pages always do (`web/next.config.ts`). The README and `security.md` say so.

## Testing

Written test-first, as in the rest of the repository.

1. **Render tests** (`scripts/tests/test_helm_chart.py`, pytest running `helm template`):
   - each role renders exactly the expected resources (a worker has no web, database, Valkey, migration Job or secret key);
   - the Ingress and HTTPRoute paths equal the path lists read from `deploy/Caddyfile` and `deploy/Caddyfile.worker`, so the two cannot drift;
   - every variable the Compose `api` services pass can be set through `config`, with the same default (except `MEGOOFLAGS_API_WORKERS`);
   - each required-value failure and its message;
   - the image tag defaults to `appVersion`; checksum annotations; one token key per worker replica; the HTTPRoute filter and timeout, and their off switches;
   - every top-level value is described in the chart README.
2. **Static checks**: `helm lint` for the three roles, and `helm template` piped into `kubeconform -strict`.
3. **Version**: `check_version.py` fails when `Chart.yaml` disagrees with `VERSION` (new cases in `test_check_version.py`).
4. **End to end on kind** (`scripts/helm_test.sh`, prints `helm OK`), with the locally built `megooflags-api:ci` and `megooflags-web:ci` images and one pinned ingress controller that serves both the Ingress and the HTTPRoute (Traefik is the first candidate; the plan confirms it supports the header filter and the timeout):
   - install a control-plane release with two API replicas and `--wait`; check `/healthz`, `/readyz`, `/sign-in`, first-run setup and a token, and that `/metrics` is 404 from outside, through the Ingress and through the HTTPRoute;
   - hold an SDK stream past the heartbeat and time a flag change through it (`scripts/proxy_stream_check.py`), through both entry points;
   - create two nodes through `/api/nodes`, install a worker release with their tokens, wait until both are ready, and read `/sdk/v1/ruleset` through the worker route;
   - scale the control plane's API to zero and check that the workers still answer;
   - run `helm upgrade` with a changed setting and check that a new migration Job ran and the pods restarted.
5. **Workflow tests** (`test_workflows.py`, `test_compose_files.py`): `ci.yml` has the `helm` job; `release.yml` packages, pushes to `oci://ghcr.io/mmhy2003/charts` and attaches the `.tgz`.
6. **Docs**: the site's `pnpm build` then `pnpm test`, with the new page and links.

The new `helm` job in `ci.yml` runs items 1, 2 and 4. `AGENTS.md` section 9 gets the same commands for local runs.

## Out of scope

- The other five Phase 2 pieces of MF-88, including control-plane HA (HA-10).
- Any API, database or web change. In particular, worker replicas that share one token ("worker pools"), which would make workers a plain `replicas: N` Deployment.
- Caddy or automatic HTTPS inside the chart; TLS comes from the cluster.
- Autoscaling (HPA), PodDisruptionBudgets and NetworkPolicies.
- High availability or automated backups for the bundled PostgreSQL. For production the README points to a managed database or an operator through `externalDatabase.url`.
- Chart signing, an Artifact Hub listing, and OpenShift-specific settings.
- Tested Argo CD support (documented only).
